**Checked 30 September 2026.** Put this file in the root of the actual hackathon repository, then open that repository in Codex. ## 1. Locked decisions

| Area | Decision |
|---|---|
| Product backend | Keep the existing FastAPI application, PostgreSQL data model, API/business logic, authentication, document processing, and tests. |
| Frontend | React + TypeScript + Vite + Tailwind CSS. Use shadcn/ui for functional components, Lucide icons, and a few Magic UI components for visual character. |
| API boundary | Browser calls relative `/api/...` URLs. FastAPI owns the business logic and database access. |
| Deployment | One repository, one public Railway **web application service** that serves the built React app and FastAPI API. The existing PostgreSQL database is a separate Railway **database service**; keep it. |
| Architecture graphic | [`tt-a1i/archify`](https://github.com/tt-a1i/archify) to make one source-backed diagram for the pitch. This is the Archify skill chosen in the earlier discussion, not the unrelated `archify-cli` project. |
| Promo video | [`latent-spaces/brag`](https://github.com/latent-spaces/brag) after the product works, using actual product screens and claims. |

Do not add another frontend framework, a second API, another visual component library, or a second public web service just to accomplish this migration. Adapt existing templates and routes incrementally so working flows remain usable until their React replacements pass checks.

## 3. One-time preflight and installation

Run these from the **actual repo root**. Codex can execute them if it has terminal and network access. The commands below install tools or create files; they do **not** deploy the app.

### 3.1 Check the machine

```bash
git --version
node --version
npm --version
python --version
ffmpeg -version
codex --version
```

Use **Node 22.12 or newer**: current Vite accepts Node 22.12+ (or 20.19+), while `/brag` requires Node 22+. Install Python at the version required by the existing backend, not an arbitrary new version. FFmpeg must be on `PATH` for `/brag` rendering. [Vite](https://vite.dev/guide/), [/brag](https://github.com/latent-spaces/brag/blob/main/README.md)

If Node is too old and you already use `nvm`, the exact upgrade is `nvm install 22` followed by `nvm use 22`; otherwise get a Node 22.x installer from the [official Node.js downloads](https://nodejs.org/en/download). For FFmpeg, common package-manager commands are `brew install ffmpeg` on macOS/Homebrew or `sudo apt-get update` followed by `sudo apt-get install -y ffmpeg` on Ubuntu/Debian. On Windows, use a build linked from the [official FFmpeg download page](https://ffmpeg.org/download.html) and confirm `ffmpeg -version` works in a new terminal. System-level installs may require your machine's administrator approval. On Windows, `py --version` can be used if `python --version` is unavailable.

If using the terminal Codex CLI and it is missing, the current [official OpenAI Docs](https://learn.chatgpt.com/docs/codex/cli) give this macOS/Linux installer:

```bash
curl -fsSL https://chatgpt.com/codex/install.sh | sh
```

Then run `codex` and complete the first sign-in. If using the Codex desktop app already, no CLI install is required. On Windows or where that installer is unsuitable, use the platform-specific option on the linked official page. Account sign-in can require the human account owner.

### 3.2 Scaffold the frontend only if `frontend/` does not already exist

```bash
npm create vite@latest frontend -- --template react-ts
cd frontend
npm install
npm install tailwindcss @tailwindcss/vite
npm install -D @types/node
```

The Vite scaffold syntax and `react-ts` template are current. Tailwind's current Vite path installs `tailwindcss` plus `@tailwindcss/vite`. [Vite](https://vite.dev/guide/), [Tailwind](https://tailwindcss.com/docs/installation/using-vite), [shadcn Vite guide](https://ui.shadcn.com/docs/installation/vite)

Codex should set `src/index.css` to import Tailwind and should merge React, Tailwind, the `@` alias, and the development API proxy in `vite.config.ts`:

```css
@import "tailwindcss";
```

```ts
import path from "path"
import react from "@vitejs/plugin-react"
import tailwindcss from "@tailwindcss/vite"
import { defineConfig } from "vite"

export default defineConfig({
  plugins: [react(), tailwindcss()],
  resolve: { alias: { "@": path.resolve(__dirname, "./src") } },
  server: { proxy: { "/api": "http://127.0.0.1:8000" } },
})
```

Also add the matching `@/*` → `./src/*` alias to **both** `tsconfig.json` and `tsconfig.app.json`, following the [current shadcn Vite guide](https://ui.shadcn.com/docs/installation/vite). Change the proxy target if the existing FastAPI dev server uses a different local port. Keep `src/index.css` imported by the React entry point.

## 5. FastAPI and Railway connection

The intended browser flow is:

```text
Browser → Railway public domain → FastAPI web service
                                ├── /api/* → existing business logic → PostgreSQL service
                                └── UI paths/assets → Vite production build
```

In development, Vite proxies `/api` to FastAPI so the browser can use the same relative URLs. In production, FastAPI serves the built `frontend/dist` files. Current FastAPI documentation offers `app.frontend("/", directory=..., fallback="index.html")`, which gives normal API routes priority and handles client-side navigation. **Use it only if the installed FastAPI version supports it**; otherwise implement and test static assets plus SPA fallback in the existing app's style. Do not let a catch-all swallow `/api`, `/docs`, health routes, auth callbacks, or downloads. [FastAPI frontend guide](https://fastapi.tiangolo.com/tutorial/frontend/)

Codex should inspect existing Railway settings before selecting a build strategy. If the current build cannot produce both Python dependencies and `frontend/dist`, adapt its build configuration or use a multistage Dockerfile. Railway detects a root `Dockerfile` automatically; do not add one if the current setup already handles both stages. The **web** process must listen on `0.0.0.0` and Railway's `$PORT`. Keep the PostgreSQL service and reference its `DATABASE_URL` from the web service; never bake that value into frontend code or a Docker image. [Railway Dockerfiles](https://docs.railway.com/builds/dockerfiles), [Railway port guidance](https://docs.railway.com/networking/troubleshooting/application-failed-to-respond), [Railway PostgreSQL](https://docs.railway.com/databases/postgresql)

The exact Railway start command and Dockerfile `COPY` paths depend on the actual Python module, package manager, and repo layout. Codex must derive them from the repo and then run a local production-mode smoke test. A generic `uvicorn main:app` line is **not** safe to paste into an unknown project. Keep the database secret on the server; do not use a `VITE_` variable for it, because Vite client variables are built into browser assets. [Railway frontend variables](https://docs.railway.com/guides/frontend-environment-variables)

## 8. Pre-hackathon checklist, in order

### The day before

1. **Put this file in the repo root.** Add the short `AGENTS.md` pointer if useful. Confirm Codex opened the intended Git repository.
2. **Create a safe checkpoint.** Commit or save the current working app and note the current Railway URL. Keep a rollback route.
3. **Run the version checks in §3.1.** Get Node 22.12+, FFmpeg, Git, the backend's Python version, and Codex ready. Sign in to the accounts that the team actually needs.
4. **Install Archify and `/brag` locally.** Restart Codex, confirm both `SKILL.md` files exist, and run `npx hyperframes doctor`. Make a tiny throwaway video test, then delete only that test output if desired.
5. **Check Railway.** Confirm the existing web service, PostgreSQL service, database reference, public domain, environment variables, and spending limits. Record who can approve deployment. Do not put values in notes or Git.
6. **Prepare sanitized demo data.** Use documents, screenshots, and product claims you have permission to show. Decide the one core task judges should see.
7. **Start frontend integration.** Have Codex inspect before editing, implement the core flow, build it, and run backend tests. Fix deployment locally before the event clock starts.

### On hackathon day, before judging

8. **Run the complete user path** in local production mode and at the Railway URL: load → authenticate if needed → input/upload → analysis → result → export. Refresh a nested frontend URL and inspect the browser console.
9. **Freeze features.** After the core flow works, spend the remaining time on legibility, speed, empty/error states, and the demo path.
10. **Generate one Archify graphic** from the final code/deployment and verify each arrow. Export a high-resolution slide image.
11. **Generate the `/brag` promo** from the finished app. Watch the entire MP4 with sound and correct factual or visual mistakes.
12. **Record a full backup demo** locally, separate from the short promo. Rehearse a 2–3 minute live pitch and keep the architecture graphic, MP4, and backup recording accessible offline.
13. **Submit the verified artifacts and URL.** Check the event's actual deadline, format, and required fields. Have a human make the final factual check.

## 9. Definition of done

- Existing FastAPI behavior, authentication, document processing, database access, and tests still work.
- React UI calls actual `/api` endpoints and completes the real user journey.
- Frontend production build succeeds; FastAPI serves it without breaking API routes or client-side navigation.
- Existing Railway web service and PostgreSQL service work together, with secrets only on the server.
- Desktop and mobile layouts, loading/errors, and keyboard/focus behavior are usable.
- Archify diagram matches the deployed system; video shows real UI and honest claims.
- Live demo, short promo, architecture graphic, and backup recording are ready for judging.
